# Ass: architecture and codebase map

Updated whenever the structure, a decision or a verified limit changes.

Last verified: 2026-11-24 on macOS 27.2 (arm64), `cef` crate 156.7.0, CEF 156.0.31, Chromium 156.0.8078.100.

## Goals

Every decision below is judged against these.

- A browser for daily use on Chromium, with a small Rust shell around it: fast to start, light on memory and disk.
- One interface for people and for AI agents. What an agent may do is opt-in, authenticated and logged, and a person can watch it happen in the tab.
- Anyone can build it, fork it and run it without an account or a service of ours.
- A person's data can move between their devices through a server they run themselves. Not built yet.
- The sandbox stays on, and no security feature is turned off to make something work.
- Nothing here is more complicated than its job needs.

## Process model

| Process | Binary | Sandboxed | Role |
|---|---|---|---|
| Browser | `Ass.app/Contents/MacOS/Ass` | No, by design | Windows, tabs, profile, policy. All privileged work. |
| Helpers | `Ass.app/Contents/Frameworks/Ass Helper*.app` | Yes (verified per process) | Renderer, GPU, network service, storage service. |

The engine is `Chromium Embedded Framework.framework` inside the bundle. Both binaries load it at runtime.

The window has no title bar: macOS's three window buttons sit in the sidebar's top row. It holds Alloy-style browser views: the shell view (the browser's own UI, 272 px wide, always `ass://shell/`) and one view per tab, of which only the active tab's is visible. A tab's view fills the rest of the window and shows its page as a card: a margin of 12 px above and below and 16 px on the right, in the sidebar's colour, and corners of radius 10 (known issue 25). The shell page is the only page of its origin; every other browser is refused all `ass:` addresses.

## Lifecycle

**Startup** (`main.rs`): load framework → set API version → read the command line → refuse a profile folder that cannot be used (`profile.rs`: a path that is not absolute, is not a folder, cannot be read, or is named in `ASS_PROFILE_DIR` and missing; or the default folder when the home directory is not there) → refuse the stand-in keychain on the default profile → read the test window mode, and refuse it without the stand-in keychain → create `AssApplication` → `execute_process` → the keychain gate (`keychain.rs`, decision D8) → the default profile folder is made if it is missing, and the start ends if the profile folder is not there (known issue 27) → this profile's leftover helpers are ended (`leftover.rs`, known issue 2) → build `Settings` → `initialize` → app delegate and menu → `run_message_loop`. Each refusal ends the process with exit code 64 before `NSApp` exists; the gate ends it with 77; a profile folder that is not there after the gate ends it with 64.

**First window** (`app.rs`): `on_context_initialized` creates the `Handler` client, registers the `ass` scheme handler, and creates the shell view and the window. `on_window_created` sets the window's colour, adds the shell view, hands the window, its layout, the shell view and the client to `tabs::init`, makes the strip above the page card a handle for the window, opens the first tab (the `--url=` value on the command line, else the start page), then shows the window. In test window mode the first `show()` waits for `applicationDidFinishLaunching:`, because a window shown before launch finishes gets the app activated (verified facts 21 and 22).

**A tab** (`tabs.rs`): one Alloy browser view, a child of the window. `tabs::open` creates the view hidden and adds it to the window (CEF creates the browser during the add), then makes it the active tab unless it opens behind. Activating shows the new view, hides the old one and lays out. The page gets the keyboard when the user caused the switch; when a page caused it (a popup, a tab that closed itself), only if the shell view does not hold the keyboard.

**A popup**: allowed only from a tab, after a user gesture, while not quitting and under 500 tabs. It becomes a tab (`on_popup_browser_view_created`), and so do its own popups. A link opened with Cmd, Shift or the middle button is cancelled and opened again as a tab of ours, for `http` and `https` only (known issue 16). A DevTools window is left to CEF.

**Closing a tab**: the sidebar, Cmd+W and the page's own `window.close()` all ask the page first (`close_browser`). When the page agrees, CEF calls `do_close`; we answer 1 and post the teardown: the tab leaves the model, the next tab becomes active (its opener if still open, else the next in the list, else the previous), the view is taken out of the window and the last reference to it is dropped, which destroys the browser. Only the shell, or a browser in a window other than the main one, answers 0 from `do_close`, because 0 closes the browser's whole window. Closing the last tab leaves the window and the sidebar. A leave-site prompt is shown only for the active tab or for a close we asked for, which first brings that tab forward; any other is answered "leave" without being shown.

**Dialogs**: the engine shows none that is modal to a tab (known issue 15). `alert`, `confirm` and `prompt` are answered without being shown; HTTP auth challenges are cancelled; a client certificate request continues without one; the File System Access pickers and the device choosers are refused by a content setting; WebAuthn is hidden from pages. The leave-site prompt and the print panel are AppKit's and stay.

**Quit** (`mac.rs` → `tabs.rs` → `handler.rs`): `terminate:` and the window's close button start it. The tabs are asked one at a time, the active one first, then the first in the list; the next is asked when the one before is gone. With no tab left the window closes and the shell with it; when the last browser is gone, the cookie store is flushed with a bound of 2 s (`flush.rs`, known issue 2), then `quit_message_loop` → `shutdown()` in `main`. "Stay" on a leave-site prompt stops the quit (Chromium sends `cancelTerminate:`); the tabs closed before it are not brought back (known issue 18). While quitting, `open`, `navigate` and popups are refused, and every further quit request asks again.

**Second launch on the same profile**: `initialize` returns 0 in the new process, which exits 0. The running instance gets `on_already_running_app_relaunch` and shows its window.

## Shell channel (`src/shell.rs`)

- Shell page to Rust: a same-origin `fetch`, POST, to `ass://shell/api/<command>`, with a JSON body of exactly the expected fields, at most 16 KiB. Commands: `ping` and `state` (`{}`); `open` and `navigate` (`{"input"}`: a new tab, or the active tab); `activate` and `close` (`{"id"}`); `back`, `forward`, `reload`, `stop` (`{}`, on the active tab).
- Threads: the check of who is asking, and the parsing, run on the IO thread. `ping` is answered there. Every other command is posted to the UI thread, where the tabs live; the check is made again there, and the reply is sent afterwards. A task that is dropped unrun answers with a refusal, so no request is left waiting.
- Replies: `state` is `{tabs:[{id,title,loading}], activeId, address, canGoBack, canGoForward}`, in list order. `open` and `navigate` reply `{"ok":true,"went":"address"|"search"}`; the rest `{"ok":true}`. Tab ids count up from 1 and are never reused in a run. A refusal is a 4xx with `{"error":"<fixed text>"}`. A request that fails the first check gets no reply at all.
- Rust to shell page: three constant scripts that carry no data. `ass-state`, at most once every 50 ms: the page then fetches the state. `ass-focus-address` (Cmd+L) and `ass-new-tab` (Cmd+T).
- Text a web page controls travels only as JSON: each title cut to 256 characters, the address to 2048 bytes and stripped of any user name and password. A page with no title of its own shows its host. At most 500 tabs.
- Typed text (`src/address.rs`): `http:` and `https:` addresses are taken as typed; text that looks like a host gets `https://` (`http://` for `localhost` and IP addresses); text with a space, and everything else, is a search; an address with a user name or password, a control character, or any other scheme is refused. Nothing typed is logged.
- Who is answered: only the shell browser's main frame, decided in the browser process. Commands also require that frame to show the shell page. The page and its two assets are fixed bytes and are served to that frame whatever it shows.
- What moves the window: the regions the shell page marks (`-webkit-app-region`, its top row), cut to the shell view, at most 64, and a fixed strip 12 px high above the page card. Every browser reports its page's regions; only those of the shell's main frame are taken, so no web page can make any part of the window a handle or take one away. Reviewed for security, by reading.
- Navigation policy: the shell view may only load `ass://shell/` and opens no popups. Every other browser is refused all `ass:` URLs.
- What keeps other code out of the shell origin is the page's content policy (own script files only, nothing inline, nothing from elsewhere) and Trusted Types, not the checks above.
- The page (`src/shell_ui/`): a request to Rust that is not answered in 5 s counts as a lost channel. Suggestion rows are built only when the user types, so a page cannot move a row under the pointer; a row for another tab starts with "Switch to". If the active tab changed after the user began to type, Enter opens a new tab and does not load into the tab that came forward.
- Recovery: if the shell's frame leaves the page or its renderer ends, the page is loaded again, at most 3 times in 60 s. After that it stays dead until restart.

## Build

- `cargo run --bin bundle` → `target/debug/app.noindex/Ass.app`. Add `-- --release` for `target/release/app.noindex/Ass.app`. Spotlight does not list a folder whose name ends in `.noindex`, so a build never shows beside the app in use, and the tests run builds from there.
- The installed app is `target/release/Ass.app`. `scripts/install.sh` copies the release build there. No build or test writes to it.
- Needs `cmake` and `ninja`. Does not need Xcode (no `.xib`; the menu is code). The Rust toolchain is pinned in `rust-toolchain.toml`.
- The bundler signs the app ad hoc, from the inside out (the framework's libraries, the framework, the five helpers, the app), with `/usr/bin/codesign`, and fails unless `codesign --verify --deep --strict` then passes. Before signing it gives each helper CEF's identifier (`dev.ass.browser.helper`, `.helper.gpu` and so on); the pinned crate gives them all the app's own. Both tools are part of macOS. No identity yet: known issue 1.
- First build downloads CEF (about 470 MB) into `.cef/<version>/`.
- The bundler removes `CARGO_PKG_*` and `CARGO_MANIFEST_*` from the nested `cargo build`. Without that, `ring` recompiles on every run.
- The app's icon is `resources/mac/Ass.icns`, a committed file, so a build needs nothing to draw it. To redraw it: `design/app-icon/build.sh` (needs Google Chrome).
- To move to a new Chromium: change the exact `cef` pin in `Cargo.toml`, rebuild, run `scripts/smoke.sh`. Then read the limit of the Mac's teardown watchdog in the new version (known issue 2): anything of ours that depends on its 10 s goes or changes with it.

## Data locations

- Profile: `~/Library/Application Support/Ass`. `ASS_PROFILE_DIR` overrides it for tests; empty counts as not set.
- On every start the profile folder exists, as a folder, before Chromium starts (known issue 27). A folder named in `ASS_PROFILE_DIR` must already exist: the app never makes it. A path that is not absolute, is not a folder, or cannot be read is refused. So is the default folder when the home directory it lies in (`HOME`) is not there. Each of these ends the start with exit code 64, before anything is opened or written. The default folder is made by the app when it is missing, for its owner only, after the keychain gate.
- With the stand-in keychain or test window mode, the profile must not be the default profile folder; otherwise the start is refused with exit code 64 and nothing is written. Folders are compared by device and inode only, which is one reason a named folder must exist: compared as text, a folder that does not exist yet would pass under another spelling of the default one. The default profile is recognised under `HOME` and under the account's home directory from the system's user database, since `HOME` can point anywhere. If that database cannot be read, both are refused.
- Keychain item: service `Ass Safe Storage`, account `Ass` (cookie encryption key). One item for every profile. The gate reads it before Chromium does (`src/keychain.rs`).
- `--use-mock-keychain`: Chromium's stand-in keychain, a fixed key in memory, for tests. The gate is then skipped and says so on stderr. Refused with exit code 64 on the default profile, whose cookies that key did not encrypt.
- Exit code 77: the keychain gate stopped the start (Quit at our alert, no lasting access to the key, the key not reachable while this profile or the default one holds data, or the keychain's interaction setting not readable or not restored). Nothing was changed.
- `ASS_TEST_WINDOW=invisible`: test window mode. Refused, with exit code 64 and before anything is opened, unless `ASS_PROFILE_DIR` names an existing folder other than the default profile and the command line has `--use-mock-keychain`.

## Verified facts

Commit hashes and branch names in this file belong to the project's history before it was published. That history is not in this repository.

1. Every helper process is OS-sandboxed (`sandbox_check`), and none runs with `--no-sandbox`.
2. A cookie with an expiry survives quit and relaunch.
3. Chrome-style browser: `chrome://extensions` loads, and an unpacked extension's content script runs.
4. A Chrome-style window refuses a second Chrome-style browser view, even after the first is removed: `Cannot add multiple Chrome style BrowserViews`. One ordering tested.
5. Alloy-style browser views: two in one window work, and swapping them back and forth works. A hidden view stays alive while something holds a reference to it. The same extension's content script also ran in an Alloy view.
6. The Rust bindings expose process messages, V8 handlers, custom schemes and scheme handler factories. The crate also carries its own Rust implementation of CEF's message router, browser side and renderer side (`src/wrapper/message_router.rs`); never run here.
7. Menu shortcuts Cmd+C, Cmd+V and Cmd+Q work in the release app. Checked by hand on 2026-11-23; automation cannot press keys without Accessibility permission.
8. The app can be asked to quit by PID through AppKit (`NSRunningApplication.terminate`, the same `terminate:` path as Cmd+Q) without Accessibility permission: exit code 0 in 3 s on the release app. Tests use this instead of quitting by bundle ID.
9. This CEF build does not play H.264 or AAC: `canPlayType` returns an empty string for `avc1.42E01E` and `mp4a.40.2`, and MP4 videos stay at `readyState 0`. VP9, AV1 and Opus return `probably`.
10. Network audit of the idle release app (2026-11-23): 11 runs, all exit 0, 55 helper processes all sandboxed, and the sockets seen by the OS matched Chromium's own net log.
11. Shell channel, reviewed twice for security (2026-11-23): content pages, popups and their sub-frames got no asset and no reply from `ass://shell/`, with the renderer's own checks on and with them off (`--disable-web-security`). No tested input made `navigate` load anything but `http` or `https`.
12. Quit on the shell build (same day): once, twice, in bursts, during startup (6 of 6, from 0.39 s after launch), with a popup open, with a second popup timed to open 0 to 200 ms after the quit request (19 of 19 exit 0; the popup really opened during the quit in 8 of them), "Stay" then "Leave", and with the shell dead or its renderer killed: all exit 0 with no helper left.
13. What CEF tells a scheme handler about the requester: the frame's URL changes only after the browser process has handled the commit, so a new document's first requests carry the old URL. The `Origin` header of the shell's own `fetch` is `null`. Requests from an `iframe` with no `src` are reported as the main frame's.
14. A page can change its title thousands of times a second. Setting the window title on every change grew the browser process by gigabytes and killed it after about 150 s. Set at most once every 50 ms, three runs of 200 s stayed under 212 MB and quit with exit 0. Not rerun in a popup.
15. `javascript_close_windows` disabled refuses `window.close()` only for a page with history. A page that is the first history entry can still close itself: the start page, a page it redirects to or replaces itself with, and a URL typed while the view is on its first blank page.

16. Test window mode, first attempt (2026-11-23, debug build, one launch per condition). With the activation policy set to Prohibited the app never became frontmost or active (350 samples), the policy was not reset in 16 s, and a quit through AppKit by PID exited 0 in 0.16 s with no helper left. But its window was never ordered on screen: both pages reported `hidden`, drew 0 frames and ran timers 64 to 85 times slower. An app hidden this way does not exercise rendering.
17. Same run: `Window::set_position` before the first `show()` did not hold; the window ended at `0,33`, 1280 by 800, inside the display. And when a second launch hands off to a running instance, that instance's window is ordered on screen (seen once, 82 ms after the second process started; the probe ended the app within 28 ms).
18. The framework we pin was built with Xcode 27.0 (build 27A266a) against the macOS 27.0 SDK, for macOS 13.0 and later: `DTXcode 2700` and `DTSDKName macosx27.0` in its `Info.plist`, and `sdk 27.0`, `minos 13.0` in its `LC_BUILD_VERSION`. Read on 2026-11-24.
19. Test window mode, second attempt (2026-11-24, debug build, one launch). The mode: activation policy Accessory, an application class whose `activateIgnoringOtherApps:` and `activate` do nothing, and a window made fully transparent and click-through before each `show()`. The app was started from a shell that descends from the frontmost app. It was activated 1.951 s after launch, 56 ms after its window was created, while that window was still unsized and not on screen. The foreground app lost activation for 14 ms and the probe ended the app in the same millisecond. No sample ever saw the app active: only the workspace's activation notification did, so sampling alone misses this. The app was a regular app for 23 ms before the policy was set. Cause not found. The transparent window itself was never reached, so it is neither proven nor disproven.
20. Test window mode, the experiment without Chromium (2026-11-24, one trial). Not separated yet.

## Read from the pinned sources, not run

Read on 2026-11-23 from the CEF 156.0.31 headers, the `cef` crate 156.7.0 and the Chromium source at 156.0.8078.100. None of this was run. A line moves to "Verified facts" only after a run.

- Extensions: CEF gives the embedder no extension API in either style. Extension commands exist only through `ExecuteChromeCommand`, which is Chrome style only (`cef_browser.h:1050-1051`).
- In our tab model (Alloy style) these come from us or not at all: downloads (canceled by default), camera and microphone (denied by default), other permission prompts (ignored by default), fullscreen. Every hook exists and is bound in Rust.
- No API restores a tab's back and forward history after a restart (the entries are read-only), discards or freezes a background tab, shows a window without activating it, clears one profile's localStorage or IndexedDB, reads the history database, or sets a proxy.
- Added 2026-11-24, also read and not run: freezing a tab and clearing one site's storage have a route through DevTools messages (`Page.setWebLifecycleState`, `Storage.clearDataForOrigin`), with no new API. A DevTools session bears on known issue 10.
- Since Chromium 128, Alloy-style browsers run on Chrome's own browser layer (CEF `docs/architecture.md:140,162`), and every Alloy tab gets Chrome's tab helpers (`browser_platform_delegate_alloy.cc:206`). What our tabs lack is Chrome's window and tab-strip classes, not its profile or its extension system.
- CEF itself carries 118 applied patches to Chromium, about 15,240 lines over 468 files. No page describes an embedder keeping its own patches beside them.
- A windowed browser view cannot be transparent (transparent painting is windowless only). So an HTML overlay such as the command bar would be an opaque rectangle. This is an inference from the headers.
- DevTools messages can be sent, executed and observed from Rust without a debugging port (`cef_browser.h:621-623`). This is the base for the agent interface.
- The crate's raw bindings are generated against experimental API version 999999, while our binaries declare 15600. Rule: call no method marked experimental until it is checked against 15600.
- The Rust API surface is the same on macOS, Windows and Linux.
- Added 2026-11-24, read while looking for what activates the app in test mode. `on_context_initialized` runs inside `initialize` when the profile is created synchronously, which it is for our cache path (`chrome_browser_context.cc:78-101`), so our first window exists before `[NSApp run]`. The UI message pump enters `[NSApp run]` (`message_pump_apple.mm:785-788`), so `applicationDidFinishLaunching:` reaches our app delegate. Between a window's creation and our `show()`, nothing in CEF or Chromium orders it on screen or focuses it. On our path Chromium's only activation call is `[NSApp activateIgnoringOtherApps:YES]` in the show path (`native_widget_ns_window_bridge.mm:1081`). It never sends `-activate`, `unhide:` or `setActivationPolicy:`, and does not import `TransformProcessType` or `SetFrontProcess`. Apple documents that `finishLaunching` "Activates the app" but not when, nor for Accessory apps or windows that already exist.
- `WindowDelegate::initial_bounds` cannot place a window outside every display: Chromium fits it into a display's work area. Moving the created window with `set_position` is not fitted. Read while building the test window mode. With no initial bounds CEF puts the window at the corner (0,0) with the preferred size (`views/window_view.cc:641-647`); ours are centred in the primary display's work area.
- Added 2026-11-24, read for the tab build; CEF paths are under `libcef/browser/`. What ran is in verified fact 27.
  - Teardown of a tab's view: `do_close` answering true makes `CloseContents` reset the close state (`alloy/alloy_browser_host_impl.cc:885-924`). Dropping the last reference to a view that is out of its window runs `~CefBrowserViewImpl`, then `WindowDestroyed` and `CloseBrowser(true)` (`views/browser_view_impl.cc:147-165`), which destroys the browser in the same task.
  - A popup's callbacks come in this order in the code: `OnPopupBrowserViewCreated`, `OnAfterCreated`, `OnBrowserCreated` (`alloy/alloy_browser_host_impl.cc:203-222`), which is not the order the header gives. So a popup is in our list before it can agree to close.
  - A popup view with no delegate cannot place its own popups, and CEF then opens a window of its own for them (`browser_platform_delegate.cc:41-74`, `:270-276`). That is why every tab's view gets our delegate.
  - `OnAddressChange` fires only for a committed main-frame navigation that is not an error page; a failed one fires `OnLoadError` (`browser_contents_delegate.cc:524-589`).
  - Our Alloy tabs use Chrome's own login prompt and never ask the client for credentials unless `--disable-chrome-login-prompt` is set (`chrome_content_browser_client_cef.cc:683-708`). Proxy authentication takes the same path (`login_delegate.cc:97-99`).
  - While a DevTools debugger is attached to a tab, Chromium skips what it otherwise does to that tab's dialog when the tab is hidden (`tab_modal_dialog_manager.cc:312-327`). Tests attach one, so they differ from a person there.
- Added 2026-11-24, read in Apple's published Security framework source for macOS 26.5 (tag `Security-61901.120.67`; none is published for macOS 27, which the app is verified on). The gate and Chromium both ask with `SecItemCopyMatching` and no data-protection flag; such a query is answered by the file-based keychain when the modern store gives an error. That keychain's paths are written with `~`, and `~` is taken from the `HOME` variable unless the process is app-sandboxed, which ours is not (`DLDBListCFPref.cpp:616-735`); the user database is asked only when `HOME` is not set. A new key, added with `SecItemAdd` and no keychain named, goes to the default keychain found the same way. So a start with `HOME` pointed elsewhere reads and writes only the keychain under that `HOME`. Not read: what a failed write does when there is no keychain there.

The fix, proven for the bare program by the rule written before the trials (2026-11-24, 17:18 to 17:45; three trials of 480 s, one at 200 by 200 and two at 1280 by 800, with the Mac in ordinary use): the window at level 8 (above normal windows, below the Dock and the menu bar), on every desktop, stationary, out of the window cycle and allowed beside full-screen apps (collection behaviour `0x40151`), alpha 0, ignoring the mouse. 14 desktop changes and no activation; on 5 of those landings macOS changed the frontmost app and chose another app each time. 28 presses of a mouse button began over the window and the program received none (the buttons were polled about 50 times a second; that the app underneath received them was not measured). macOS reported the window as not visible only during a desktop switch, 0.9 to 2.0 s each time. Seen and not explained: hover events reached the window (344 and 466 at full size) although it ignores the mouse and the program was inactive; in some samples a window of another process at layer 23 held ours whole while macOS still called ours visible; the window server moves the window during a switch, and it ended at x 0 each time. Not run: any of it in the app (Chromium's own window, its three buttons, its tracking areas, windows attached to ours), a landing on a desktop with no other window, and whether the pointer changes shape over the invisible window. Read at the pinned tag: nothing on our path resets the level, the behaviour or `ignoresMouseEvents` after creation; at exactly the floating level Chromium would give the page hover events while the app is inactive (`bridged_content_view.mm:446-459`), which is why the level is not 3; CEF's always-on-top call would add a behaviour that conflicts with ours, so the settings go on the `NSWindow` directly. To build: the settings in `prepare()` of `src/test_window.rs`, a read-back of level, behaviour and `ignoresMouseEvents` after the first `show()`, and the probe with them, because above the normal level its "covered" is always false and its slides and returns mean nothing. It narrows known issue 24 and does not close it: a tab opened during a desktop switch can still keep its first `visible`. In the app since `3d65eb8` (verified fact 36): 24 starts, the window at layer 8 in every launch, the settings read back after each `show()`, no activation. None of those launches had a desktop change, so in the app the case this is for has not happened yet; each launch now prints its desktop changes. Closed on 2026-11-24 (verified fact 37): four launches of the app went through 10 desktop changes between them with no activation.
24. **A tab opened behind while the window is covered, or on another desktop, is never told that it is hidden.** Read: Chromium holds a "covered" state for 1 s before it acts on it, and hiding the view cancels it (`web_contents_view_cocoa.mm:510-524`); a hidden or covered state that comes before the first visible one is not applied (`web_contents_impl.cc:12783-12800`). So such a tab keeps the `visible` it started with, and is not throttled, until it has been shown once and hidden again. Seen in test window mode only, where a covered window counts as visible (`--disable-backgrounding-occluded-windows`): checks 0.01, 0.02 and 5.07 of the tab test on 2026-11-24, with the window covered or off the active desktop. Not seen in a normal window. It will matter for agents: a tab an agent opens while the person works in another app in front of ours. CEF's `was_hidden` works only for off-screen rendering. No fix chosen.
25. **The page card's corners are rounded from outside CEF.** CEF has no call for a view's corner radius and gives no handle to a browser view's native view. `round_page_card` (`src/app.rs`) finds the window's native subview whose frame equals the card and sets its layer's corner radius, with public AppKit calls only. If CEF nests its views differently one day, the corners go square and nothing else breaks. Not seen by anyone: whether the corners flicker during a resize or a tab switch. The clean route is one call in the CEF we compile. Around the same work: the card's ring and shadow of the design are not drawn; the window's buttons stand at x 27, 50 and 73 where the design has 24, 44 and 64, because AppKit places them and no API moves them; and CEF sets the title bar's height through AppKit selectors that are not public (`_titlebarHeight`, `_shouldCenterTrafficLights`; read), so a macOS update can move the buttons.
26. **Chromium keeps browsing history and fetches site icons in our tabs by itself.** Found on 2026-11-24 in the security review of the site icon plan (D9); the profile and the log were then read. CEF gives every tab of ours Chrome's own tab helpers (`browser_platform_delegate_alloy.cc:206`) and turns history recording on (`:211-217`). Seen: one old test profile's `Default/History` held 17 addresses and 17 visits, `ass://shell/` among them. Seen: our test server's log of the tab test has `GET /favicon.ico` requests that no code of ours makes, sent as the page's own image request, one of them with the site's `SameSite=Strict` cookie; so the CEF header's sentence that an icon download sends no cookies (`cef_browser.h:516`) is wrong at the pin (`multi_resolution_image_resource_fetcher.cc:134-135`, read in that review). `Default/Favicons` exists and held no row in that profile, whose test server answers 404 for icons, so whether Chromium stores icons there is not settled. What it means: the profile holds a history that no screen of ours shows or clears, and the shell's own address is in it; the history screen and "clear browsing data" have to deal with it, and D9's own download duplicates one Chromium already makes. No CEF call hands us Chromium's icon or its history (verified by reading: "Read from the pinned sources, not run").

27. **Given a profile path it cannot make into a folder, Chromium carries on in a folder of its own.** Found on 2026-11-24 by reading the pinned sources. Never run, and not to be run on a machine in use.
    - The chain. CEF sets the profile path with `PathService::Override`, which makes the folder and fails when it cannot (`base/path_service.cc:281-299`). CEF does not look at the result (`libcef/common/resource_util.cc:126-130`). Chrome's own path provider then answers: `~/Library/Application Support/Chromium`, made if it is missing (`chrome/common/chrome_paths.cc:151-156`, `chrome_paths_mac.mm:26-41`, `:72-87`; our `Info.plist` sets no `CrProductDirName`). The profile is opened there, with our key. A cookie written under another key cannot be decrypted and takes its site group with it (known issue 22).
    - What it would have done: a start with `ASS_PROFILE_DIR` naming a file (plain `mktemp` makes one), a path below a file, or a place that cannot be written would have opened the profile of a Chromium browser installed beside ours and deleted its saved logins, or left a stray profile in the user's Library. Up to the build of `f3972e4` nothing refused such a path. No run of ours started on one: every test makes its folder first.
    - Found in the same read: Chromium makes a missing folder's parents by the path's text (`base/files/file_util_posix.cc:1234-1279`). So `/a/b/../c` with `/a/b` missing ended in `/a/c`, while the keychain gate had asked the kernel about the same text and found nothing there. With the real keychain and no key item, the gate would have let a start through onto a folder that held data. The removal of the `..` refusal at `f3972e4` opened this (known issue 2).
    - Fix (`src/profile.rs`, `src/main.rs`, `1c95900`): on every start the profile folder exists, as a folder, before Chromium starts, so nothing is left for Chromium to make. A folder named in `ASS_PROFILE_DIR` must already exist; a path that is not a folder or cannot be read is refused; each with exit code 64, first thing, nothing written. The default folder is made by the app itself, after the keychain gate, for its owner only, as Chromium makes it; if the folder is not there then, or its real path cannot be found, the start ends.
    - The default folder is made in a home directory that is there, or not at all. Our own making of it walks the path's text as Chromium's does, so a `HOME` with `..` through a missing folder would have had the keychain gate look at nothing and the app then open another home's default profile. Found by the security read of the fix, before it was built; such a start is refused first thing.
    - That read, of the working tree (2026-11-24): nothing blocks. Once both checks have passed, CEF's override cannot fail, short of a change to the path in between: for a folder that exists its `CreateDirectory` returns at once, and its `realpath` is the call ours has just made. A folder that exists and cannot be opened or written (mode 000 or 500) is not refused by us; by reading, Chromium then fails inside that folder: it cannot make its lock and ends the start with a log line and no dialog (`chrome/browser/process_singleton_posix.cc:320-328`, `:987`, `:1024-1034`; `chrome_main_delegate.cc:623-629`). Run once, outside the app: the system's `realpath` succeeds on a folder with mode 000 and on one with mode 500.
    - Cost: `ASS_PROFILE_DIR=/new/place` no longer makes the folder. Make it first.
    - How it is checked: unit tests (a file, a link to a file, `/dev/null`, a path below a file, `..` through a missing folder in the named path and in `HOME`, a locked parent, a dangling link at the default path, the default folder made and its mode) and one smoke check (a named folder that does not exist). Runs: verified fact 40. On purpose no launch names a file or an unreadable path: if that refusal failed, the app would open the other folder, and a temporary `HOME` is not shown to contain it.
    - Not covered: a change to the path between our look and Chromium's; whether Chrome's fallback folder follows `HOME`. Not run: a start on a folder with mode 000 or 500, and our own making of the default folder in the app, which needs the real keychain (verified fact 40). `CrProductDirName` is not a fix: set to our name, the fallback would be the real default profile.

Spike built and reviewed twice (verified facts 11 and 12). Cost: that channel is a security boundary we own, with its own test (`scripts/shell-channel-test.sh`). |

Decided on 2026-11-23. Compiling needs one machine with about 150 GB of working space (CEF's guide, for a debug build). Not settled: the form (CEF with our patches, or a Chromium fork), the Rust shell (D1), codec licence fees, and where it is compiled. |

Run on 2026-11-24: verified fact 24, judged by a rule written before the run. First without any prompt; if access is not granted, our own alert, one read that may prompt, and the silent check again. Only "Always Allow" lets the app start. ## Open decisions

- **The engine layer.** Its cost, and any change to the Rust shell (D1), are not decided yet.
  - Position, 2026-11-23: the stock CEF binaries cannot carry a browser for daily use. Three reasons, most certain first. They will never play H.264 or AAC (verified fact 9; the maintainer's licensing statement, read at the source). Extension APIs are unsupported in our tab model, and the maintainer declined to change that (read at the source). Security updates arrive when one maintainer builds them (as reported).
  - So the engine becomes our own build. It has two possible forms. CEF with our own patches keeps the Rust shell and this repository's build as they are. A direct Chromium fork is what every shipped Chromium browser uses, and it replaces the Rust shell.
  - How large the patch set would be, sized on 2026-11-24 by reading the pinned Chromium and CEF sources (nothing was run). Matching Arc's features needs five changes inside Chromium or CEF:
    - H.264 and AAC: no patch, two build settings, the same in both forms. The cost is the licence, which is not decided yet.
    - A tab's back and forward history after it is reopened or after a restart: small. Chromium's `NavigationController::Restore` takes a freshly created browser, and the byte format exists; the patch is two methods.
    - Freezing a background tab: no patch, through DevTools, or one small method. Discarding one: close it and restore its history later, so nothing beyond the item above.
    - Clearing one profile's site storage: small, one method beside the existing `ClearHttpCache`. Per site: no patch, through DevTools.
    - Extension buttons, clicks and popups: medium. `chrome.tabs` and `chrome.windows` over our tabs: one small patch per failing call, as CEF already does for two of them, or large if our windows had to become Chrome's own. Installs: not settled by reading.
    - Every patch that adds an API has a fixed cost: our additions go into an interface of our own, and we carry our own regenerated copy of the `cef` and `cef-dll-sys` crates.
  - What the same reading says about a fork. A fork gets Chrome's session restore, tab discarding and `chrome.tabs` for free only if Chrome's own tab strip is our tab model and our windows are Chrome's windows. Then the shell becomes C++ and Objective-C++; no supported way to drive Chrome's browser layer from Rust was found. With our own tab model, a fork calls the same Chromium APIs a patch to CEF would.
  - Reading, 2026-11-24: this points to CEF with our own patches, which keeps the Rust shell (D1). It is not decided: the extension run can still overturn it, by showing that real extensions need Chrome's whole window model.
  - Decided on 2026-11-23: we compile it ourselves (D5). The form was chosen on 2026-11-24 as the working choice: the CEF package's source with our own patches (D6).
  - What decided between the two forms: one run of extension features in our tabs (verified fact 24), judged by the rule written before it. No condition for a fork was met: every basic worked, nothing crashed the browser process, and the extension loaded without a window of Chrome's own. The list of failing `chrome.tabs` and `chrome.windows` calls is not short (15 of 24), but the errors point to one cause: our tabs belong to no window that Chrome's extension code knows. That cause is inferred from the error texts, not read in the source, and the rule asked for a short list of calls that return an error: 5 of the 15 return nothing and no error, and 2 escape into a window of Chrome's own. So D6 is the working choice, and one reading of the pinned sources comes before the first patch: where "No current window" and `windowId` -1 come from, and what giving our tabs such a window takes.
  - A compile is not needed until video has to play in the app or the first change inside Chromium is made. Until then all work runs on the ready-made package. Both forms compile the same Chromium source, and the first job is the same in both: the pinned package's source compiled with H.264 and AAC, and this app running on it. This is reasoning, not a run.
  - Where Chromium is compiled is decided when a compile is needed.
  - Rules for any machine that compiles Chromium: no signing key is ever stored on it; the steps live in this repository as a script anyone can repeat; how its output is checked is reviewed for security before any of it enters the app.
  - The risks of a rented build machine, if one is ever used (2026-11-24). A compromised machine or provider would hash its own poisoned output, and no check of ours would see it; the only real check is an independent rebuild compared file by file. So: one fixed build path, and one independent rebuild before the first release to anyone outside the project. The provider that was looked at publishes no SSH fingerprint, so the first connection trusts the one it is shown.
  - What stands either way: the HTML shell, the design of its channel, tab state in plain Rust, the typed command list, tests that stay off the screen.
  - Cost known today: compiling needs about 150 GB of working space on the machine that compiles (CEF's guide, as reported, for a debug build; a release build's need is not measured; Chromium's own figure of 100 GB is from its Linux guide, and it publishes none for the Mac). The Mac this work is done on has 41 GB free (measured 2026-11-23: M4 Pro, 12 cores, 24 GB of memory). The app itself is 330 MB, 327 MB of it Chromium (measured on the release app, 2026-11-23).
- **How a request is tied to the shell document**: the frame's URL today; a token for each load, or the frame's identifier, as alternatives. See verified fact 13.
- **Bundle identifier.** `dev.ass.browser` is a placeholder and is hard to change after release.
- **Signing identity.** A self-signed certificate is ruled out: it does not stop the keychain prompt (known issue 1). Cheapest first: stay ad hoc and answer one prompt for each new build; an Apple Development certificate from a free Apple account (Xcode once; whether it qualifies is not read); a Developer ID through the Apple Developer Program (99 USD a year, Apple's enrollment page, read 2026-11-24; needed for any release to other people). Position: ad hoc now, Developer ID when a release to others is near.
